No keys, passwords, new credentials, or manual configuration from the user are required. Frozen source artifacts, adapters, universe, cuts and production files remain unchanged.

The original instrumentation specification expressly permits "OS-access separation or encrypted archive". This revision selects OS separation. It removes RSA/AES and cryptography dependency rather than generating or hiding another user-managed key. Linux bootstrap creates three distinct locked system identities with no passwords: UID10001 capture, UID10002 outcomes, UID10003 status/supervision. Capture owns the input/candidate WAL and cannot read outcomes. The outcome process reads capture through read-only SQLite and OS permissions, cannot write it, and owns a private0700 outcome directory with0600 WAL files. The status role cannot read capture or outcomes and serves only operational JSON. Bootstrap proves reads/writes under real identities and then permanently drops root with no-new-privileges. A Windows chmod-only fallback is rejected. Root Northflank administrators retain custodian access; no researcher unseal or outcome API exists.

The separate outcome worker commits full OUTCOME records to its private append-only WAL, then publishes hash-only operational receipts in a separate worker-owned WAL. If interrupted between commits, it replays the private record into the safe receipt WAL without recomputing or duplicate acceptance. Endpoint source bytes and original version IDs are copied to the private archive for independent lossless snapshot reconciliation. Return values, endpoint prices and path payloads remain absent from public/capture records and HTTP. Capture runs no outcome calculations and receives no strategy feedback. All original +1ms receipt, scheduled/computed time, frozen candidate, feature, WAL, horizon, Parquet and retention semantics remain enforced.

Build/deploy only Dockerfile.observer from this feature branch. Runtime is `python keyless_runtime.py`; no key arguments or environment secrets. Mount a dedicated durable volume at /capture; never share the trading volume. A mounted volume and conservative32GiB free-storage qualification are required before any live readiness capture. The frozen all140-symbol24h record payloads can exceed6GB because complete history/baseline receipt arrays appear in immutable intents and accepted records. No pruning/sampling/ephemeral-only capture workaround is allowed. The cohort's60/120-day storage capacity requires separate measured qualification before activation.

A separate Northflank job can run `python keyless_runtime.py --self-test` to qualify the deployed image without keys, market capture, or readiness claims. This is synthetic operational qualification and contributes0 live audit hours.

The signed-in Northflank project shows service quota2/2 and only6GB volume sizing enabled. Larger sizes are disabled. This is an external hosting/capacity blocker for the independent lossless live observer. The trading service is left on its existing branch and existing volume.
